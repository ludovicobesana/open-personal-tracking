# open-personal-tracking Community

open-personal-tracking should be developed in public.

The community is not only an audience for the project. Contributors should be able to influence requirements, architecture, documentation, integrations, accessibility, design, translations, and roadmap priorities.

## Community principles

- Be constructive.
- Prefer evidence and reproducible examples.
- Explain tradeoffs.
- Critique ideas, not people.
- Make important decisions publicly.
- Keep contributor workflows understandable.
- Avoid governance that depends on private conversations.
- Document decisions that affect users or contributors.

## Where collaboration happens

The preferred collaboration surfaces are:

- GitHub Issues for bugs and bounded work
- GitHub Discussions for ideas, questions, and community conversation
- Pull Requests for proposed changes
- RFCs for significant architectural or product changes
- Weekly community calls for synchronous triage and design discussion
- Discord (https://discord.gg/6CjFPH55Rv) for real-time contributor chat

Discord is for quick, informal conversation. It is not a place to make or record decisions; anything material still needs to land in an Issue, Discussion, or RFC.

## Weekly community call

open-personal-tracking should hold one public issue and contributor call every week, 13:00-14:00, on Discord (https://discord.gg/6CjFPH55Rv).

Suggested agenda:

1. New contributors
2. Important regressions
3. Issue triage
4. Blocked pull requests
5. RFCs requiring discussion
6. UX/product decisions
7. Documentation gaps
8. Good first issues
9. Next week's priorities
10. Open floor

Calls should not become a private decision-making mechanism.

Any material decision made during a call must be summarized in a public issue, discussion, or RFC.

## Async first

Attendance must never be required to contribute.

People in other time zones must be able to participate asynchronously.

Before the call:

- publish the agenda
- link issues and RFCs
- invite agenda proposals

After the call:

- publish concise notes
- record decisions
- assign actions
- link follow-up issues

## Community roles

Possible roles:

### Contributor

Anyone making useful contributions.

### Reviewer

Trusted contributor able to review in specific areas.

### Maintainer

Responsible for merges, releases, triage, and stewardship.

### Module owner

Maintainer or reviewer responsible for a bounded subsystem such as backup, Android, providers, accessibility, or network.

Roles should be earned through sustained contribution rather than assigned based on status outside the project.

## Recognition

Contributions beyond code should be recognized.

Examples:

- Bug reports
- Reproduction repositories
- UX research
- Accessibility testing
- Documentation
- Translation
- Design
- Community moderation
- Release testing
- Provider maintenance

## Good first issues

Maintain a curated set of genuinely approachable issues.

A `good first issue` should:

- have clear acceptance criteria
- identify relevant files or areas when possible
- avoid hidden architectural decisions
- be small enough to review
- have an available maintainer or reviewer

## Decision transparency

For consequential changes, record:

- context
- alternatives
- decision
- tradeoffs
- migration impact
- follow-up work

open-personal-tracking should accumulate institutional memory in the repository rather than only in maintainers' heads.
